# Local onboarding and recurring-card pilot

Native candidate revisions completed fresh laptop setup against local
Northstar Superset. A separate live-Jev pilot completed card onboarding and
four recurring policy cases. These establish working paths, not enterprise
adoption or superiority over a frontier agent.

## Fresh install to first useful report

We extracted a checksummed native archive into an isolated home, ran the actual
terminal wizard, entered credentials through hidden prompts, and verified
registration with the real Codex CLI. Live catalog health reported 48 dashboards.
The optional localhost health UI also worked. The binary's production fingerprint
matched before and after the trial.

Both Luna arms used the same business request and source helpers against a real
local Superset instance containing synthetic Northstar data. SignalWeave added
its normal MCP tools. The shared dashboard helper uses SignalWeave's Superset
normalizer; the chart-row helper returns raw saved-query rows. This is not an
independent third-party Superset-MCP comparison.

Both reports completed. The latest SignalWeave report qualified September/August
bucket arithmetic rather than claiming a confirmed like-for-like decline, did
not invent currency, separated funnel revenue from net sales, and asked for
the context needed before unattended alerts. Independent agent review checked
the arithmetic and found minor wording issues; no real human panel participated.

The observed report times were 100 seconds for baseline and 157 for SignalWeave.
One pair is not a speed benchmark, and this run did not use Jev for a recurring
decision. [Setup and report evidence](human-native-onboarding-2026-10-13.json).

A later fingerprint-verified build repeated this journey from a locally packaged
archive: the real wizard finished, Codex registration was verified, live Superset
health passed, and both first reports completed. Observed times were 173 seconds
for baseline and 162 for SignalWeave; this second pair still establishes no speed
advantage. The actual binary also passed the one-line install/PTY setup test using
a simulated release transport. Neither exercise proves a published download or
real human usability. [Current-build evidence](current-native-human-onboarding-2026-10-13.json).

## Reviewed card to recurring decisions

The separate pilot used generated monthly channel-balance records and a local
read-only company-MCP simulation—not a live Superset extraction. An agent asked
the simulated owner for context, obtained data-expert sign-off and independent
simulated owner review, then reused one approved card.

All four live Jev judgments and both agents' structured outcomes matched the
fictional policy: quiet/no recipient, investigate/Analytics, notify/Leadership,
and missing primary evidence/Data Trust. Each pair had the same reviewed card,
notes, source tools, model and limits. All completed; no transport failures or
test-limit exclusions remained. Jev responses took 270–355 ms in these four calls.

That is **four functional cases, not “100% enterprise accuracy.”** The report
utility proxy was essentially tied. A treatment recommendation omitted a clear
historical-replay caveat; structured correctness does not establish a complete
human-facing quality pass. Delivery stayed disabled throughout.
[Protocol and results](northstar-native-recurring-pilot-2026-10-13.json).

## What remains

The subsequent natural-workflow trials exposed additional gaps. With weakened
optional-tool guidance, both agents completed four cases correctly but the
treatment never used Jev; that is not Jev evidence. Restoring the production MCP
guidance exposed a payload fallback that dropped measurement values and shortened
the policy. Three native judgments were wrong, although the frontier agent
recovered the correct final outcomes. A test-only citation gate also rejected
valid receipt references, invalidating a natural latency comparison.

The first corrected payload preserved the policy and facts, but a newly onboarded
five-watch card exceeded the unchanged token guard in three healthy cases. Only
the missing-source case reached Jev. The next change preflights independent
question batches against the same complete state, rather than discarding facts
or raising the token limit. Source dependencies are now explicit in simulated
owner review: a globally required source cannot silently become a prerequisite
for an unrelated policy branch.

The next completed four-case run had healthy live Jev requests, correct final
agent outcomes in both arms, and six source-supported mock recipient messages.
Its native routed decisions were correct in only two cases. In the quiet case,
low support changed a correct raw `ignore` selection into `investigate`; in the
notification case, the raw selection was already `investigate`. The frontier
agent recovered the owner's intended outcomes. This is not native decision
accuracy or an end-to-end advantage. A test citation gate also rejected actual
source URLs, requiring retries; its timings cannot establish a natural speed
comparison. [Captured outcomes](native-cadence-dialogue-pilot-2026-10-13.json).

A bounded twelve-request sensitivity experiment replayed these four saved
requests. Changing only the outcome question to apply the owner's ordered
policy improved raw selections from three of four to four of four. Routed
outcomes were still only three of four: notification support remained below the
unchanged action floor. Removing metadata was tested separately but is **not**
a production change. The control responses were cached, the cases were known,
and there was one call per cell; this is diagnostic evidence, not a benchmark
or independent holdout. [Inputs, results and limits](native-policy-input-sensitivity-2026-10-13.json).

These cohorts are retained separately rather than pooled with the earlier four
passing Jev cases. The next fresh owner-dialogue pilot completed onboarding and
all four paired cases. Its four live native routed decisions and both agents'
final outcomes matched the policy; independent review supported all six recipient
messages. It retained two malformed evaluation attempts, a receipt lookup error,
and a test-only alias-collision retry. The treatment took longer in every case.
That is a functional pass, not a quality or speed win.
[Fresh pilot evidence](native-cadence-owner-channel-pilot-2026-10-13.json).

The twelve-period expansion completed fresh onboarding and all 24 agent runs,
using twelve live Jev calls without budget censorship. Baseline outcomes and
routing matched in **12/12** cases; SignalWeave's final agent matched **10/12**;
native routed decisions matched **6/12**. Median recurring episode times were
22.7 seconds for baseline and 42.2 for treatment. This cohort does not establish
an advantage. It is retained in full, not replaced by the passing pilot.
[Twelve-period protocol and results](native-cadence-twelve-period-2026-10-13.json).

One final failure was a frontier misread: it treated onboarding-example dates as
a fixed recurring constraint although the approved card used a relative monthly
window. Another omitted the incomplete current month. Investigation found that
the production MCP bridge replaced live partial/non-comparable comparison
contracts with static catalog contracts. The durable receipt also omitted those
contracts, so its evidence pages could not recover the missing source quality.
The candidate now preserves live quality without letting the source redefine
catalog meaning, records inspected contracts in receipts, and prioritizes them
in compact handoffs. Required scalar coverage bindings and numerical-analysis
bindings are now distinguished in guidance and simulated owner review.

The native failures also expose an analytical boundary: Jev must not be treated
as an exact calculator or segment counter. [TypeSafe's documented limitations](https://docs.typesafe.ai/model-jaggedness/jev-1.13)
support keeping those operations in code or the calling agent's analysis. These
sources supplied observations, not validated decompositions; no numerical
condition was fabricated to turn the result into a pass. The focused rerun is a
known-regression check, not an independent holdout or proof of enterprise value.
A successful API request, a correct raw
selection, a routed decision and a useful final message remain separate scores.

Test independently varied business cases and natural recurring cadences, including
onboarding effort, total cost, concise recipient messages and source drift. Then
validate with actual people and customer data. Earlier invalid fixtures and
censored runs were retained separately, not counted as wins.
