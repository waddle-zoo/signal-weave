# Meridian Cloud: what the larger onboarding trial exposed

The initial pair did **not** prove a working recurring workflow. The capable
baseline returned useful provisional analysis; SignalWeave reached two draft
cards but timed out before approval or Jev evaluation. The failed attempt stays
in the [compact record](../../evaluations/data/meridian-onboarding-diagnostics-2026-10-19.json).

## The actual experiment

Meridian is a fictional subscription company with 5,000 accounts, overlapping
revenue/cash definitions, multiple currencies and 118 discoverable assets. Eight
as-known weekly snapshots contain 136,330 source events at the first cutoff and
155,892 at the last. **Only the first cutoff was executed by analysts.**

Both arms used fresh Luna sessions, the same four real read-only company-MCP
tools, source definitions, simulated colleagues and retained workspaces.
Treatment additionally received the checksum-verified native executable, its
bundled skill and documented shared-context extension. No analytical SQL or
card was supplied. The MCP is a custom typed-export source, not a hosted BI
vendor or proof that an arbitrary existing MCP needs no integration work.

| First onboarding attempt | Company tools + Luna | SignalWeave + same tools |
| --- | --- | --- |
| Elapsed seconds | 370.06 | 1,208.10 |
| Completed work | Provisional cash/renewal report and runbook | Two draft cards; no completed workflow |
| Analyst uncached input / output tokens | 115,663 / 42,633 | **Unknown after timeout**, not zero |
| Colleague replies | 3 | 6 |
| Live Jev requests | 0 | 0 |

Baseline colleague calls additionally used 13,535 uncached input / 475 output
tokens. Its checked currency-separated figures matched the raw source, but
owner preferences remained open. Its runbook also claimed an owner question
that the recorded exchanges do not contain. Useful analysis is not completed
onboarding or delivered recurring reports.

## What needs fixing

**A lab capacity error.** The small example MCP's one-million-instruction guard
rejected a normal current-subscription aggregation that direct read-only SQLite
completed in about 26 milliseconds. Independent review reproduced it; valid
optimized raw queries also worked. Thirteen treatment query calls hit this
guard. This is a source-fixture confounder, not a SignalWeave defect, and makes
product cost/UX comparisons from those repairs invalid.

**A real integration diagnostic gap.** The agent registered a new query locator
but supplied an underlying table locator as the reader's returned resource.
Native inspection correctly rejected the mismatch, but named no offending
field. Diagnostics now identify constant field names without returning remote
values. The guide explains identity arguments, the existing MCP-manifest CLI
path, compact reviews, and advisory versus policy-critical context. No identity,
tenant, source-scope or approval check was removed.

**An incomplete human conversation.** The baseline's first answer left choices
for the requesting owner. A real person could answer; the original next scripted
request instead assumed agreement. The separately frozen forward method adds an
actual owner reply and analyst continuation at the same cutoff, with shared
budgets. The owner may explicitly delegate exact technical/card review to the
data expert after intent and scope are clear—not invent policy or authorize
scheduling/external sends. First useful findings should not wait for completed
card setup.

## Review and claim boundary

Independent internal data, product and process reviews checked source integrity,
actual communication and trial validity. The source reviewer recomputed all
eight snapshots and renewal populations from raw tables; that validates the
reference, not eight successful agent reviews. Admission for unstarted waves
was withdrawn; the original admission, timeout and unknown usage remain intact.

The next run is forward testing, not a rescore or external peer review. This
initial pair establishes neither Jev decision accuracy nor an enterprise, speed or cost
advantage. Evaluating delivered work and separately checking simulated-human
fidelity follows [agent-evaluation guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
and the concern studied by [UserProxyBench](https://arxiv.org/abs/2609.38043).

## Forward first pair: approved cards, but an invalid replay clock

A separately admitted forward pair used native commit `154281e`, the corrected
source-capacity profile, and an actual first-answer/owner-reply/continuation
conversation. The source retained its read-only, two-second and row limits.
The analyst still wrote every analytical query and card.

The baseline's first interaction and owner reply completed before a controller
bookkeeping exception. Administrative recovery preserved their exact working
and delivered files, exchanges and costs; it ran only the pending continuation.
That original incomplete controller record remains unchanged. This is not a
clean replication or a replacement for the earlier timeout.

| Forward first onboarding | Company tools + Luna | SignalWeave + same tools |
| --- | ---: | ---: |
| Completed analyst interactions | 2 | 2 |
| Elapsed seconds, including recovered work | 893.51 | 1,182.91 |
| Analyst uncached input / output tokens | 248,587 / 95,836 | 381,556 / 129,870 |
| Simulated-colleague replies | 18 | 9 |
| Colleague uncached input / output tokens | 66,178 / 1,663 | 52,114 / 1,226 |
| Live Jev requests | 0 | 2 |

All usage above is known. Treatment saved two approved cards, reviewed shared
definitions and fixed query sources. Its two Jev requests used 13,711 input and
285 output tokens combined, with **no context overflow**. Provider round trips
were 0.274 and 0.205 seconds; complete native evaluations, including source
reads, were 1.245 and 0.842 seconds. These narrow timings are not workflow savings.

**The replay was temporally inconsistent.** Both cards retained a 24-hour age
limit, while the immutable July 6 source was evaluated against October's real
clock. Native code therefore produced `insufficient_data` for both. Jev's raw
choices were `investigate` and `ignore`, not those final gated outcomes. This
does not establish Jev policy accuracy or a product freshness failure. Later
paid waves were held and the coordinator closed after both actors finished;
none of the seven later cutoffs ran.

Independent source checks support treatment's historical cash amounts and its
1,668-renewal roster. The baseline's 1,723 renewals reflect a different
owner-consented horizon endpoint, not 55 fabricated or missed records. Neither
report treats an empty prior ledger window as proof of zero cash. One treatment
message ambiguously labels the correct June 29–July 6 interval as “July 6–29.”
The original message is retained, not silently corrected.

**The whole human workflow is still unproven.** Treatment's two local messages
went to the owner and Data Operations, not Finance and Customer Success.
Fewer messages therefore do not demonstrate fewer useless alerts. Its cards
have no delivery methods, so `notify` was not even offered to Jev. Such a card
can support a caller-owned routine report, but cannot prove native notification
routing. Delivery-disabled evaluation does not require empty route metadata.
The baseline's complete roster exceeded the simulated reader's 256 KB attachment
cap; that lab limit is not a SignalWeave or real Slack limitation.

Two exact card snapshots were actually opened by the simulated owner. However,
the helper's “does not change native status” wording was echoed alongside
explicit approval for evaluation, leaving consent about recording native status
ambiguous. Reviewers classified this as an instrument/clarification issue, not
a confirmed authorization breach or an unqualified approval success.

The next experiment must separate historical replay from current freshness,
clarify planned recipients versus actual sending, and grade delivered reports
and later reuse. A correct source read, persisted card or fast Jev call does
not substitute for that outcome. No comparative advantage is established here.

### Isolating the clock mismatch

A separate two-call component diagnostic reconstructed both original provider
states exactly, then changed only the engine's source-age clock to the historical
cutoff. Cards, source values, SQL and policy were unchanged. Both stale-source
blocks disappeared: the final outcomes were `investigate` (support 0.57) and
`ignore` (0.79). The two requests used 13,233 input and 285 output tokens;
original trial records remained unchanged.

This isolates the clock confound, not onboarding or alert accuracy. Neither card
offered `notify`, no recipient received a report in this diagnostic, and it was
not a native-binary rerun. A prospective historical continuation needs an actual
owner-reviewed replay policy, not silently relaxed freshness for production data.
