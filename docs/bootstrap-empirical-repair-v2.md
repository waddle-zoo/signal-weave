# Bounded authoring repair: development regression

Declare this follow-up before dispatch. Preserve the failed v1 trial at frozen
commit `5abd4d3`; do not change its labels, cards, requests or recorded scores.

## Diagnosis and change

The first trial accepted one of three authored cards. Expert controls passed
all twelve monitoring cases. The accepted finance card got four outcomes right
but omitted the policy's investigation destination on one unseen branch.
Other drafts guessed unsupported execution settings or failed schema validation.

The wrapper had not made its operator-owned execution profile explicit. A
registry-free snapshot trial cannot execute bounded follow-up retrieval. A
model-selected confidence floor of 1.0 is not an accuracy guarantee and blocked
otherwise correct Jev judgments at 0.99 support. These are configuration failures,
not evidence that Jev misunderstood those business rules.

The repair supplies and binds an explicit fixed-snapshot profile using existing
defaults: fixed retrieval, no follow-up stage, 0.70 model-support floor and
24-hour freshness limit at each historical replay clock. The model still authors
the business policy, questions, watch conditions and outcome-to-destination map.
No business condition, fixture label, numeric value, source, expert card, Jev
judgment prompt or production confidence default changes.

Generic authoring guidance is also shipped in the actual MCP instructions/schema:
use business fields and normal defaults, preserve approved source declarations,
and cover all owner-requested delivery branches, not just the supplied examples.
The optional caller-owned `examples/investigation_agent/onboarding.py` bridge
accepts free-form business fields and exact approved source/destination keys.
Code copies approved connection declarations and endpoints; the model no longer
authors the persisted card schema or runtime settings. Its output is compatible
with the existing `draft_insight_card` arguments. The research bridge exercises
the same conversion before calling the library compiler/evaluator, not the MCP
draft endpoint itself. This is a combined interface/guidance repair, not an
experiment isolating the causal effect of any single change.
This remains a research wrapper around the library evaluator, not an installed
connector/discovery or human-approval usability test.

The baseline validator in v1 rejected seven valid current source/fact identifiers
because it accepted only `adapter|resource`. Preserve its original accepted
submission score, but inspect the rejected arguments separately. Do not call a
citation-format rejection a semantic mistake. Going forward, resolve only exact,
unambiguous identifiers present in the current evidence; reject unknown,
ambiguous or previous-period fact IDs. No label-based aliasing or string guessing.

## Budget and success criteria

- Same three companies and same nine setup / twelve monitoring snapshots.
  They are now development cases, not a fresh holdout.
- Three fresh saved-login Luna author episodes; at most two tested candidates
  each. Freeze accepted cards before monitoring, with no Luna correction afterward.
- Maximum 40 additional Jev attempts, zero retries. With v1's 32 attempts, the
  combined ceiling stays at 72. Failed calls count.
- No new baseline or expert-control episodes. Their v1 evidence is retained, not
  represented as a concurrently measured control for changed authored cards.
- Freeze code/data/prompts before execution; preserve every failed attempt.
- Target: three accepted cards and twelve exact native outcomes, destinations and
  required evidence sets. Report missing runs and every component independently.
