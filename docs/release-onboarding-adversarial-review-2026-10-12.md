# Adversarial review: fresh install to useful reports and repeated alerts

Date: 2026-10-12 (evidence added through 2026-10-13 02:03 UTC)

Scope: current native release candidate, install and default-agent guidance, provider readiness, source/context behavior, approval semantics, and the current evaluation harness. This is a source/evidence review, not a release certification or customer validation.

## Decision

There is still no evidence in these artifacts of a real person downloading the reviewed candidate, connecting their own BI source to their configured Codex client, completing first-use analysis, and setting up a useful repeat alert. The current evidence supports a narrow native runtime smoke and synthetic-source trials only; it does not establish working end-to-end user benefit.

The candidate verified in the current proof is `0.2.0rc2`, source SHA-256 `22498e8a38a937a29a4d06987ef297bd7a5e2fbe7f8a170d952c7f67a9c0f11c`, binary SHA-256 `4dbc21d4bbf07a6979bc82f200aab2cc541c60c3f9f31e7b594a9eb87c2b1521`, commit `114614ae0ab080e77023ad175bad05d977ea0d4c`, dirty source, marked frozen. The README and local-install guide direct first-time download users to `v0.2.0rc1`, while describing newer setup/provider behavior as source-candidate-only; the checked-in docs therefore do not demonstrate the reviewed candidate's install-to-agent path. The parent has since reported a bounded compact-response source fix; the source tree now differs from this proof, so 4dbc/22498 is historical for that post-fix source and must not be used to validate it. This review did not publish or merge anything and makes no claim about GitHub state.

The current native smoke (`docs/evidence/release-rc2-2026-10-12-native-22498e8a.json`) records isolated setup, a default ten-tool MCP handshake from a different working directory, one live Jev `notify` on an approved synthetic card (delta `-20`), and process-restart receipt replay. It records one current-candidate installer PTY test passed/three deselected and 175 focused tests passed. This is useful packaging/runtime evidence. It is not a real BI-service test, completed human onboarding, a final business report, repeated alert evidence, or comparative quality proof. OpenAI Decisions and ChatGPT-plan readiness checks are source/offline evidence, not live end-to-end runs; the current native smoke exercises Jev only.

The follow-up bounded-receipt source patch is not represented by that native proof. A focused source test run in this review passed 12 cases, but is not a latest-binary/live validation. The judgment remains in the durable receipt (`receipt.outcome`), and a full receipt read remains available; do not describe the compact handoff as a replacement for that audit record.

The Superset leg tied to 4dbc/22498 is a native-binary run against a loopback HTTP fixture that returns Superset-shaped REST payloads, not a Superset container or service. It extracted a synthetic chart with 400 numeric observations. The refreshed artifact says `healthy=true` but still shows zero visible catalog items and says live access/permissions remain unverified. The approved-card result says `source_count=null` and explicitly marks the earlier zero as an invalid measurement (the runner read a nonexistent field); the actual count is unknown. It returns `investigate` despite the fixture policy's expected `ignore`, and the pre-fix “compact” MCP result is 595,094 bytes. One Jev request used 7,421 input and 50 output tokens in 247 ms. The parent reports a source-level payload bound since this run; this old binary/evidence does not validate the fix. The outcome/health interpretation remains unresolved. Do not call this real Superset onboarding or explain away the label disagreement until a newly fingerprinted run resolves it.

Two company-pilot attempts are retained. Attempt 01 failed before installed setup because the shared-runner verifier was called with an unsupported phase; it records 0 agent calls and 2 planned pairs not run. Attempt 02 passed binary checks before/after and reached the installed-binary `setup` invocation in two isolated synthetic company homes, but both setup invocations failed before Codex/agent launch. Its summary correctly says `not_run`, `agent_calls=0`, `intended=2`, `not_run=2`, and `agent_accuracy=null`—this is not 0% accuracy or an agent outcome. Its retained company rows reduce the cause to the generic `installed binary setup failed`, without exit code/stdout/stderr, so the evidence cannot yet tell whether the product rejected the harness's manifest/flags or the fixture setup itself is invalid. A separate native PTY smoke passed a different isolated setup path; that does not explain this failure. The working-tree transport now adds bounded redacted setup diagnostics, but attempt 02 predates that capture and remains the record of failure. Do not classify either attempt as a live agent trial.

## P0 — release and evidence gates

### Candidate install/docs parity is not demonstrated

The README's install command pins `v0.2.0rc1` and says newer provider integrations and installer flow are not in that download ([README](../README.md#L14), [README preview note](../README.md#L30)). `docs/local-install.md` also calls rc1 the published preview and separates the newer source candidate. This is a blocker for claims that the documented fresh-install path exercises the reviewed candidate, not a defect in the pinned rc1 command. Acceptance requires a distributable artifact/checksum matching the candidate and a fresh install through the exact documented route. Counterexample: the guide promises the current provider/setup experience while the install command launches a binary that predates it. This review did not publish or merge a candidate.

### Resolved setup regression; current smoke is narrow

The root parser's `--build-info` action now uses `default=argparse.SUPPRESS`, so ordinary setup no longer forwards a spurious `build_info` argument into `setup_local()` ([`cli.py`](../src/signalweave/cli.py#L64)). The three previously failing setup entry tests passed after that fix, and the current native proof records isolated setup. This resolves that source/packaging regression only; the smoke does not establish that a new human can connect real BI data and receive an accepted report from their actual agent.

## P1 — high-impact product and evaluation gaps

### Pre-fix Superset-shaped run demonstrates an evidence/context and outcome problem

The evidence identifies its source as “loopback HTTP fixture; not an actual Superset container.” Its native binary used an isolated home and the default `agent` profile. The fixture records 13 dashboard-scoped chart-data requests, two saved-query fallback posts, and a 400-observation chart snapshot of 171,625 bytes; the dashboard snapshot is 192,542 bytes. The chart has no comparison-window contract or analytical comparisons. The card is approved by a synthetic reviewer, with workflow acceptance `unassessed` and no delivery methods. Its expected policy says to report retrieved typed rows and choose `ignore` when no owner-defined exception applies. Yet the completed result is `investigate`, with no response error. The refreshed evidence correctly retracts `source_count=0` as a bad harness measurement; actual source count remains unknown. The artifact does not retain the raw evaluation result, so this review cannot determine whether the mismatch comes from card construction, source extraction, incomplete typed evidence, or provider judgment.

Keep this mismatch as a failed/unknown outcome, not a dropped episode or a policy rewrite. A diagnosis should capture a redacted card/source contract summary, selected resource/observation counts, exact typed evidence availability, and deterministic result fields, while preserving the original run. The 595 KB result is a concrete pre-fix context defect: “compact” removed duplicated renderings but did not bound structured evidence. The parent reports a source fix; acceptance still needs a rebuilt candidate whose embedded source fingerprint matches, plus a current-binary response measurement and tests that preserve required facts. The acceptance counterexamples remain: 100/500/5,000 raw observations with long/nested values; a late row that changes the correct report; explicit count/cursor and incomplete-evidence status. Never truncate silently or turn an unexamined tail into an all-clear.

**Recheck after the compact-bound patch:** the prior section-directory counterexample is resolved in source. The helper now caps the directory at 50 entries/12 KiB, reports total and completeness, caps the summary at 24 KiB with 4 KiB per field, and performs a final serialized-size check that raises rather than returning an oversized handoff. The receipt page now reports `coverage` (`partial_section`/`complete_section`) and `section_complete`, including on a tail page. The single-oversized-scalar path remains intentionally non-chunked: it returns an explicit pointer instructing the caller to request the full audit, without truncating the value. Treat that as a disclosed context-size limitation, not silent data loss; full-audit output can still be large. One MCP-envelope gap remains: `get_decision_receipt` wraps the bounded page with receipt metadata but does not check the final combined response size. A synthetic 30,201-byte page plus valid maximum-length receipt fields (including 100 120-character delivery keys) serialized to **44,472 bytes**, over the 32 KiB page target. Bound or explicitly fail on the complete tool response, and add this envelope case to acceptance. Focused tests and synthetic probes below confirm the directory cap, metadata failure behavior, and tail-page marker. This is source-only review pending the rebuilt binary; it does not validate a live provider run.

There is also a health/catalog discrepancy: `health --live` exits zero and now reports `healthy=true`, but still reports zero visible catalog items and says live source access/permissions remain unverified, while subsequent fixture chart requests return data. The fixture may not model all catalog endpoints/permissions, or health's status mapping may be overly permissive; the present artifact cannot distinguish these. A successful chart extraction must not be relabeled as a healthy real Superset connection.

### P1. Onboarding must separate report value from alert readiness

The current agent guide puts a scope-qualified report before unresolved alert policy and asks only for missing context. That is the right product direction: unknown alert criteria may pause recurrence without blocking supported analysis. Keep the two user outcomes separate:

1. A useful immediate report: inspected source refs, period and population/grain, returned values, bounded interpretation, caveats/data gaps, and a useful next question/action.
2. Alert readiness: only after unresolved definition/materiality/ownership questions receive explicit owner answers, the card is reviewed and explicitly approved, and shadow behavior is checked. Approval is not delivery authorization.

The earlier Northstar run's useful prose is tied to the superseded `01293548… / 2e0a939f…` candidate; it is historical and must not be attached to the 4dbc/22498 build. Neither company attempt produced report evidence: one failed provenance-stage validation, and the next failed binary setup before any agent call. The synthetic fixture has separately authored owner-persona answers for four journeys, but the selected 2-pair pilot uses journeys 03/05 with known initial policy and does not test report → owner clarification → resumed onboarding. A real first-use journey and a synthetic post-clarification path are different questions; neither can be inferred from these no-agent runs.

### P1. Candidate source contract strictness is a safety gate; the Northstar blocker was fixture parity

Historical finding, superseded in part by the [later real-source diagnostic](evidence/domain-context-preview-2026-10-14.md#full-raw-source-workflow-attempt-first-answers-worked-onboarding-unfinished):
ordinary Superset inspection was subsequently shown to lack these custom
contracts even when its saved aggregation was valid. Current onboarding keeps
missing declarations unverified but permits owner-approved, delivery-disabled
evaluation with recipient mappings intact. Known incompatible windows and
required comparison checks remain enforced. Neither the older strict gate nor
the newer warning path certifies unattended delivery.

For automatic routes, onboarding requires typed source-owned metric/comparison/population/grain/window evidence. Do not relax that gate based on owner prose. In the Northstar replay, the public catalog omitted a typed comparison contract that the private replay snapshot carried; `MCPSourceAdapter.inspect()` trusts the catalog descriptor and replaces the response contract. That is a fixture/catalog mismatch, not proof that the live Superset adapter lacks the contract. For report-only work, retain the useful report path without pretending the automatic card is ready. If a required contract is missing, say which exact field/resource is absent and ask whether the source has an adapter-owned definition; do not make the agent invent “versioned typed contract” metadata the actual schema does not support.

Separate source defect remains in numeric-condition binding: `onboard_insight_card()` binds caller-proposed comparison keys into a source's `required_comparison_keys` before validating the condition against that set ([`onboarding.py`](../src/signalweave/onboarding.py#L1970), [`onboarding.py`](../src/signalweave/onboarding.py#L1988)). A bounded in-memory probe previously showed a catalog key `checkout-conversion` and proposed key `invented-change-key` both ending up in the saved source requirement. Validate against the immutable inspected contract before binding. Regression counterexample: a model supplies a plausible but nonexistent comparison key and receives a saved card instead of an authoring-time rejection. Keep numeric conditions optional when the connector has no exact typed comparison.

SignalWeave does not itself schedule or send the message.

### Fairness and report-quality limits in the paired runner

The current protocol correctly declares a synthetic source MCP, default `agent` profile, the same Luna 6 xhigh setting for both monitoring arms, delivery disabled, private labels, and a maximum Jev budget of 40. It retains both no-agent failures rather than scoring them as accuracy. The frozen selection is two pairs: journey-03/later-02 and journey-05/later-01. Neither attempt proves agent quality, provider judgment, report usefulness, or repeated alerts.

For a valid final-output comparison, keep the intervention honest and record enough to explain a difference:

- The protocol gives both arms the same source MCP tools and the same treatment-authored signed card/notes during recurring monitoring, with equal Luna 6 xhigh settings and alternating order. That is a controlled *warm-card* comparison: it does not estimate fresh onboarding or the benefit of creating the card, because the baseline gets the card too. In addition, the harness calls `evaluate_insight_card` before the agent arms and passes that parent-triggered bundle to treatment ([`installed_workflow_trial.py`](../evaluations/installed_workflow_trial.py#L680), [`installed_workflow_trial.py`](../evaluations/installed_workflow_trial.py#L712)). This can test the incremental value of the whole SignalWeave evaluation-plus-handoff on a shared card, but not whether a Codex agent naturally chooses the tool. Keep the source tools equal as specified; record the bundle as the intervention, and avoid “natural tool use” or cold-start benefit claims.
- The harness invokes an ephemeral `codex exec` process with the requested model/effort, `--ignore-user-config`, and `multi_agent` disabled. This is a real Codex CLI model turn in the study sandbox, not a human using their own newly connected Codex setup or a multi-agent/subagent run. Do not equate the coordinator's six review workers with the evaluation arm's agent count.
- Gold outcomes are in private sidecars and source tests check that public model context omits labels. Preserve per-run public-input and private-label digests and request-capture assertions. Owner-policy text returned on request is context, not a gold label; synthetic HIL must be authored before labels are applied and supplied identically to both arms.
- Deterministic scoring appropriately checks exact outcome, recipients, evidence refs, metrics, scope/window, and required questions. It cannot score whether a report is useful, causally cautious, concise, or asks the right next question. The evaluator itself marks narrative review required; add blinded, arm/order-hidden independent human scoring before making a final-output quality claim.
- Retain one row for every planned slot, including setup/model/source/tool/scorer failures, timeouts, exhausted budgets, and not-run cases. State per-arm completion and failure denominators, not just accuracy among completions. Record every attempt and any provider/CLI internal retry; do not silently rerun failed episodes. Separate cold install/setup/first report from warm repeated periods. Report measured tokens, tool/source calls, latency and usage-known status; don't invent dollar cost if billing is unavailable.

### Minimum test that answers “does this help a real person?”

First establish feasibility with a real person following the exact candidate download/install instructions in a disposable new home, connecting a real read-only BI account and their actual Codex MCP client, then asking an uncoached business question. Do not seed the catalog/card/destination, supply a hidden owner answer, or have the parent call evaluation on the agent's behalf. Save the redacted tool/source trace and a short final report with source refs, period/scope, observed facts, caveats, and missing-context questions. Record setup completion, wall time, errors, source reads, and whether the person can explain what happens next. The current rc2 evidence and two company attempts do not meet this gate.

A single successful person-run shows feasibility, not benefit. For a minimum benefit comparison, use the same person/source/task with counterbalanced direct-Codex and SignalWeave conditions, same model and reasonable time/read budgets, and blind the final-report reviewer to arm/order. For a cold-start claim, the direct-Codex arm must not receive a pre-authored SignalWeave card; if both arms share one, label the result warm-card incremental value only. Keep deterministic correctness checks separate from blinded usefulness/trust ratings and publish all intended/failure denominators.

To test alert handoff without sending to Slack or another external recipient, approve one benign shadow rule, then point the caller-owned delivery path at a disposable local agent-owned capture sink. Assert the exact recipient/action payload, stable idempotency key, and that a retry/replay does not duplicate the captured action. Mark this “local sink simulation,” not delivered alert, real Slack integration, or user acceptance. External delivery remains outside the current product contract.

## Acceptance gates and counterexamples

1. **Package and prove the candidate.** Provide a distributable artifact/checksum matching the reviewed candidate, install it through the documented route, and verify source/binary fingerprints before setup and report certification. Counterexample: same version string but binary built from pre-fix source.
2. **Fresh human to useful agent output.** In an isolated home, use the actual default profile and a real provider/source; complete guide → search/inspect → exact selected-source onboarding → review → owner authorization → shadow evaluation → concise final report. Keep report-only success available while alert policy is pending. Counterexamples: guide names a full-only tool; provider guidance says Jev under OpenAI; setup succeeds but the agent cannot produce a useful scoped report.
3. **Prove evidence budget behavior.** Test 100/500/5,000 observation payloads and adversarial section counts/long keys with explicit serialized-byte and token budgets; require every returned compact response to stay within 64 KiB (or fail explicitly), the complete `get_decision_receipt` page response within 32 KiB (or fail explicitly), explicit `partial_section`/`complete_section` state, exact counts/cursors, and no silent truncation. Preserve decision-critical judgment and evidence or visibly fail incomplete. Oversized scalar content currently requires the explicitly disclosed full-audit path and may exceed ordinary context; do not treat it as bounded-page support.
4. **Keep source semantics typed and honest.** Exercise actual Superset when an available runtime exists; otherwise label loopback HTTP payloads as fixture. Cover missing contracts, nulls, partial pages, stale data and source errors. Counterexample: health says zero sources while fixture extraction is counted as connected, or a plausible invented comparison key is accepted into a card.
5. **Separate authorization, acceptance, and side effect.** A current approved card remains shadow-only until acceptance and caller-owned scheduling/delivery safeguards are explicit. Counterexample: a receipt is treated as an alert sent, or a retry duplicates a downstream message.
6. **Run fair paired final-output evaluation.** Freeze card and source inputs, hide labels, retain both reports and evidence reads, and blind narrative reviewers. If the treatment includes a parent-triggered evidence bundle or different tools, describe that entire product-surface intervention. Counterexample: score only the native typed decision and claim better agent analysis.
7. **Keep all denominators and claim limits.** Publish planned/completed/failed/not-run counts, retry/timeouts, cold vs warm costs and limitations. Counterexample: a zero-call `invalid_preflight` row disappears and the remaining successful slots are called an accuracy rate. No fixture or finite trial is “customer validation” or “100% proof.”
